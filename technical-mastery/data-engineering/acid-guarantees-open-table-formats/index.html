5.1 - One-Line Definition

ACID Guarantees in Open Table Formats - The mechanism by which open table formats (Apache Iceberg, Delta Lake, Apache Hudi) provide database-grade ACID transactions on object storage (S3, GCS, ADLS) through: Atomicity (a transaction commits all files or none via metadata pointer swap), Consistency (schema and partition invariants enforced in metadata), Isolation (snapshot isolation via immutable snapshot IDs - readers always see a consistent snapshot, not partial writes), and Durability (committed metadata is durable on object storage with CRC checksums) - enabling concurrent reads and writes on the data lake without a database server.

5.2 - Why It Exists

Object storage (S3, GCS) has no built-in transaction semantics. s3:PutObject on 100 Parquet files is 100 separate API calls. If the process crashes after 50 calls, the table is in a partially-written, inconsistent state. Concurrent readers may see half the data. A “rollback” requires listing all files, determining which were part of the failed write, and deleting them manually - complex, error-prone, and not atomic.

Traditional data lakes (Hive + Parquet on S3) had no solution. Hive’s transaction support (ACID on ORC tables) was a workaround limited to Hive. When Spark jobs wrote to the same Hive table concurrently, they would overwrite each other’s files silently.

Apache Iceberg (Netflix, 2017), Delta Lake (Databricks, 2019), and Apache Hudi (Uber, 2016) independently solved this problem: move transactional semantics into the TABLE FORMAT (a metadata layer on top of Parquet files on S3). The metadata layer tracks: which Parquet files are “active” (in the current snapshot), which commits have occurred, and which were rolled back. ACID properties are implemented via metadata management, not via a database server.

5.3 - Core Concepts and Terminology

Snapshot (Iceberg): An immutable, consistent view of the table at a point in time. Each commit creates a new snapshot. The snapshot points to a list of manifest files that list all active data files. Readers always read a specific snapshot ID; they never see partial writes from concurrent transactions. The current snapshot is the tip of the snapshot chain.

Transaction Log (Delta Lake): An append-only directory of JSON files (_delta_log/00000000000000000001.json) recording every transaction. Each log file describes: files added, files removed, and metadata changed. The current table state = replay of all log entries from 0 to N. Delta Lake checkpoints the log every 10 transactions (Parquet file of all adds/removes up to that point) to avoid replaying from the beginning.

Timeline (Hudi): Hudi’s equivalent of the transaction log. A .hoodie metadata directory recording: instants (individual commits with timestamps), actions (COMMIT, ROLLBACK, COMPACTION, CLEAN), and states (REQUESTED, INFLIGHT, COMPLETED).

Optimistic Concurrency Control (OCC): The mechanism used by all three formats to handle concurrent writes. Writers do NOT lock the table. Each writer: (1) reads the current snapshot/log version, (2) writes new data files (Parquet), (3) attempts to commit a new metadata entry that references the current snapshot/log version. If the current snapshot has changed since step 1 (another writer committed), the commit FAILS with a conflict. The writer retries from step 1. This allows reads to never block and multiple writers to proceed optimistically (betting they won’t conflict).

Snapshot Isolation: A transaction reads from a consistent snapshot of the table at its start time. Even if concurrent writes commit during the transaction, the reader’s snapshot does not change. The reader sees a consistent, immutable view. Snapshot isolation prevents: dirty reads (never; all reads are from committed snapshots), non-repeatable reads (never; same snapshot throughout), and phantom reads (no new rows appear mid-transaction in the same snapshot).

Schema Evolution: Adding, removing, or renaming columns without rewriting existing data files. Iceberg supports: adding columns with defaults, removing columns (marked as deleted in metadata, old files still have the column), renaming (ID-based column tracking, not name-based). Metadata records the schema version; readers apply the appropriate projection for each file.

Partition Evolution: Changing the partition strategy (from month-based to day-based partitioning) without rewriting existing files. Iceberg supports this natively: new files use the new partition spec; old files use the old spec. The metadata tracks both partition specs. Hive: partition change requires full table rewrite.

Time Travel: Reading the table as it was at a past snapshot or timestamp. SELECT * FROM table TIMESTAMP AS OF '2024-01-01' returns the data at that point in time (using the snapshot that was current at that timestamp). Implemented by reading the historical snapshot from the metadata rather than the current snapshot.

Hidden Partitioning (Iceberg): Partition values are computed from column values, not stored in the file path. For PARTITIONED BY MONTHS(order_date): the partition value is derived from order_date at write time and stored in manifest metadata. Readers apply the partition predicate at metadata scan time (which manifest files to read), not at file listing time. No user-visible partition column in queries.

5.4 - Evolution / History

2012-2018 - Hive on HDFS: Hive tables on HDFS: directories as partitions (/orders/dt=2024-01-01/). No transactions. Concurrent writes: last writer wins. “Dynamic partition overwrite” as a manual workaround (Spark writes to temp directory, then atomic rename on HDFS - exploiting HDFS rename atomicity).

2016 - Apache Hudi (Uber): Uber’s “Hadoop Upserts anD Incrementals.” Designed to support upserts (merge into) on HDFS for near-real-time analytics with CDC ingestion. COW (Copy-on-Write) and MOR (Merge-on-Read) storage types. First open-source format with ACID-like behavior on Hadoop.

2017 - Apache Iceberg (Netflix): Netflix’s solution to Hive’s scaling problems (table with 700,000 partitions, Hive Metastore overwhelmed). File-level tracking: manifest files track individual Parquet files (not directories). Snapshot isolation. Schema and partition evolution. Open-sourced and donated to Apache (2018).

2019 - Delta Lake (Databricks): Databricks open-sourced Delta Lake. Transaction log (JSON-based). ACID transactions on Spark. Strong integration with Databricks platform. DML operations: UPDATE, DELETE, MERGE INTO. Rapid enterprise adoption via Databricks.

2021-2024 - Open Table Format standardization: The three formats compete and converge. Apache XTable (Universal Table Format): bi-directional translation between Iceberg, Delta Lake, and Hudi. Iceberg becomes the cloud provider standard (Snowflake Iceberg Tables, BigQuery Iceberg, AWS Glue Iceberg support). Delta Universalization: Delta tables readable as Iceberg via UniForm.

5.6 - Mental Model / Analogy

Iceberg transactions are like Git commits on data files. In Git: you check out the current HEAD (read current snapshot), make changes (write new data files), stage them (write manifest files), and commit (write new metadata pointing to the new files). If someone else pushed to the same branch while you were working, your push is rejected (conflict). You pull their changes (retry from their new snapshot) and push again.

The data files are like source code files. The manifest is like the Git index. The metadata file is like the commit object. The version-hint is like the branch pointer. Snapshot isolation: like Git’s detached HEAD mode - you read the exact state at one commit, unaffected by subsequent commits.

Time travel: like git checkout <commit-hash>. You see the exact state of the data at that commit’s snapshot. The files are still there (unless explicitly compacted and cleaned up).

5.7 - Common Misconceptions

Misconception 1: “Delta Lake, Iceberg, and Hudi are equivalent”

Reality: The three formats have architectural differences with practical implications:

  • Atomicity mechanism: Delta Lake uses JSON transaction log (one entry per commit). Iceberg uses metadata file (snapshot chain). Hudi uses timeline directory.
  • Concurrency control: Delta Lake supports optimistic concurrency on Databricks; S3-based Delta lacks distributed lock support (requires DynamoDB lock table). Iceberg uses atomic file rename (S3 eventual consistency workaround via catalog-level CAS).
  • Schema evolution: Iceberg: column ID tracking, renaming without breaking. Delta Lake: name-based column tracking, renaming requires rewrite or alias.
  • Cloud support: Iceberg: first-class in Snowflake, BigQuery, Athena, Glue. Delta: first-class in Databricks, Delta Sharing. Hudi: first-class in AWS EMR.

Neither format is universally “best.” Choose based on your compute engine and cloud platform.

Misconception 2: “ACID on Iceberg is as strong as PostgreSQL ACID”

Reality: Iceberg provides snapshot isolation, NOT serializable isolation. Serializable isolation prevents all anomalies (dirty reads, non-repeatable reads, phantom reads, AND write skew). Snapshot isolation allows write skew: two transactions both read the same snapshot, both decide to write based on what they read, both commit without conflict (they wrote different rows). Result: logical inconsistency even though both “committed.”

Example: Constraint “total orders per customer < 100.” Transaction A reads customer X has 99 orders. Writes order 100. Transaction B (concurrent) also reads 99 orders. Writes order 100. Both commit. Customer X now has 101 orders. No conflict detected (they wrote different files). For invariant enforcement: implement application-level constraint checks.

Misconception 3: “Iceberg ‘tombstones’ deleted files immediately”

Reality: Iceberg DELETE operations write “delete files” (position deletes or equality deletes) that mark rows as deleted. The underlying Parquet data files are NOT immediately removed. A COMPACTION job rewrites the data files (merging deletes). The old data files are not CLEANED (GC’ed) until an expireSnapshots() operation runs AND the files are outside the snapshot retention window. Until then: deleted rows are still physically on S3 (hidden by metadata). This matters for GDPR right- to-erasure: data is not truly deleted until compaction

  • expire + GC runs.

Misconception 4: “Time travel is free”

Reality: Time travel requires the historical snapshots and their data files to still be on S3. If the expireSnapshots() operation has been run (to control storage costs), historical snapshots are deleted. Time travel to a snapshot that no longer exists fails with a SnapshotNotFoundException. The retention period (how long historical snapshots are kept) is the time travel window. Retention trade-off: longer retention = more time travel range = more S3 storage cost.

5.9 - Failure Modes and Debugging

Failure Mode 1: Concurrent Write Conflict Loop

# SCENARIO: 50 Spark jobs write to the same Iceberg table.
# Each job: small incremental load (100K rows each).
# Iceberg's optimistic concurrency: each writer retries
# on conflict. With 50 concurrent writers and a 30-second
# commit time:
# Writer 1 commits -> Writers 2-50 all conflict.
# Writer 2 retries, commits after writer 1 -> Writers 3-50 conflict.
# ... N conflicts, N-1 retries per writer.
# Total retries: O(N^2) = 50^2 = 2,500 retries.
# Pipeline runtime: 50 jobs x 5 retries avg = 250 serial commits.

# ROOT CAUSE: Too many concurrent small writers.
# Fix: Coalesce small writes.

# BAD: 50 separate small Spark jobs writing individually
for hour in range(50):
    spark.createDataFrame(hourly_data[hour]).writeTo(
        "catalog.db.orders"
    ).append()  # Each append: potential conflict with all others

# GOOD: Combine into fewer larger writes
# Option 1: Merge small batches before writing
all_data = spark.createDataFrame(
    [row for hourly in hourly_data.values() for row in hourly]
)
all_data.writeTo("catalog.db.orders").append()  # One commit

# Option 2: Write to staging tables, then one merge
for hour, data in hourly_data.items():
    spark.createDataFrame(data).writeTo(
        f"catalog.db.staging_{hour}"
    ).createOrReplace()

# Single merge from all staging tables
spark.sql("""
    MERGE INTO catalog.db.orders t
    USING (
        SELECT * FROM catalog.db.staging_0
        UNION ALL SELECT * FROM catalog.db.staging_1
        -- ... union all staging tables
    ) s
    ON t.order_id = s.order_id
    WHEN NOT MATCHED THEN INSERT *
""")

Code walkthrough: Optimistic concurrency scales poorly with many concurrent small writers: each retry requires re-reading the current snapshot, re-writing the manifest, and re-attempting the commit. With 50 concurrent writers and a busy table, a single writer may retry 10-20 times. The GOOD pattern consolidates: either merge all data before writing (one commit, no conflicts possible) or write to separate staging tables (no conflicts because each writer uses a unique staging table name) then perform a single MERGE (one commit on the final table). One large commit is almost always preferable to N small concurrent commits for ACID tables.

Failure Mode 2: Orphan Files (No Cleanup Running)

SCENARIO: Iceberg table with daily loads for 1 year.
  Each daily load writes ~1GB Parquet files.
  Each failed load (5% failure rate) writes partial files
  that are NEVER committed (because the commit fails
  or the job crashes after writing files but before commit).
  
  After 1 year:
  - Committed files: 365 x 1GB = 365GB
  - Orphan files (uncommitted): 365 x 0.05 x 1GB = 18GB
  
  More critically: old snapshot files (snaps 1-355)
  are no longer needed but still exist.
  After 2 years: 18GB orphans + 365GB of old snapshots
  (all 365 prior year's snapshots, each pointing to files
  that still exist).
  
  S3 storage cost: $0.023/GB x 730GB = $16.79/month extra
  
PREVENTION (run as scheduled maintenance jobs):
  // Spark Iceberg maintenance
  // 1. Expire old snapshots (frees snapshot retention)
  spark.sql("""
    CALL catalog.system.expire_snapshots(
      table => 'db.orders',
      older_than => TIMESTAMP '2024-01-01 00:00:00',
      retain_last => 5
    )
  """)
  
  // 2. Delete orphan files
  // (files on S3 not referenced by any snapshot)
  spark.sql("""
    CALL catalog.system.remove_orphan_files(
      table => 'db.orders',
      older_than => TIMESTAMP '2024-01-01 00:00:00'
    )
  """)
  
  // 3. Compact small files (improve query performance)
  spark.sql("""
    CALL catalog.system.rewrite_data_files(
      table => 'db.orders',
      strategy => 'sort',
      sort_order => 'order_date ASC'

Iceberg MERGE INTO with concurrent read safety:

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .config("spark.sql.extensions",
            "org.apache.iceberg.spark.extensions"
            ".IcebergSparkSessionExtensions") \
    .config("spark.sql.catalog.hive_prod",
            "org.apache.iceberg.spark.SparkCatalog") \
    .config("spark.sql.catalog.hive_prod.type", "hive") \
    .getOrCreate()

def merge_cdc_into_orders(cdc_df) -> dict:
    """Merge CDC (Change Data Capture) records into
    Iceberg orders table with full ACID guarantees.
    Returns commit statistics."""

    # Register CDC data as a temp view
    cdc_df.createOrReplaceTempView("cdc_staging")

    # Iceberg MERGE INTO - handles INSERT, UPDATE, DELETE
    # This is ONE atomic transaction:
    # - All matching rows are updated
    # - Non-matching new rows are inserted
    # - DELETE marker rows physically delete target rows
    # If this fails mid-way, the entire merge is rolled back.
    spark.sql("""
        MERGE INTO hive_prod.orders.fct_orders AS t
        USING (
            SELECT *,
                   ROW_NUMBER() OVER (
                       PARTITION BY order_id
                       ORDER BY change_time DESC
                   ) AS row_num
            FROM cdc_staging
        ) s
        ON t.order_id = s.order_id
           AND s.row_num = 1  -- Deduplicate CDC events

        WHEN MATCHED AND s.cdc_operation = 'DELETE'
            THEN DELETE

        WHEN MATCHED AND s.cdc_operation = 'UPDATE'
            THEN UPDATE SET
                t.status = s.status,
                t.amount_cents = s.amount_cents,
                t.updated_at = s.change_time

        WHEN NOT MATCHED AND s.cdc_operation = 'INSERT'
            THEN INSERT (
                order_id, customer_id, amount_cents,
                status, order_date, created_at, updated_at
            ) VALUES (
                s.order_id, s.customer_id, s.amount_cents,
                s.status, s.order_date, s.change_time,
                s.change_time
            )
    """)

    # Verify the commit: read the table's snapshot history
    history = spark.sql("""
        SELECT snapshot_id, committed_at, operation,
               summary['added-records'] AS added,
               summary['deleted-records'] AS deleted
        FROM hive_prod.orders.fct_orders.history
        ORDER BY committed_at DESC
        LIMIT 1
    """).collect()

    if history:
        snap = history[0]
        return {
            "snapshot_id": snap.snapshot_id,
            "committed_at": snap.committed_at,
            "added_records": snap.added,
            "deleted_records": snap.deleted
        }
    return {}

Code walkthrough: The MERGE INTO statement is a single atomic Iceberg transaction. It handles three CDC operations in one commit: DELETE (physical row deletion via Iceberg equality deletes), UPDATE (mark old file rows as deleted, write new file with updated values), and INSERT (write new file with new rows). The deduplication ROW_NUMBER window ensures that if multiple CDC events arrived for the same order_id, only the most recent is applied. The post-merge history query uses Iceberg’s metadata tables (table.history) to verify the commit: the snapshot_id, rows added, and rows deleted are recorded in the snapshot summary. Concurrent readers who started before this MERGE are unaffected - they continue reading the pre-MERGE snapshot.

5.12 - Scale Behavior

At 10x (1TB table, 10 concurrent writers, 1M row loads):

Iceberg: OCC works well for 10 writers. Conflict rate < 5% (writers commit fast). Maintenance: expire snapshots weekly. File count: ~1,000 Parquet files. Compaction: monthly.

At 100x (100TB table, 50 concurrent writers, streaming):

Iceberg: conflict rate increases with concurrent writers (see failure mode 1). Solution: Iceberg’s write distribution mode (RANGE partitioning by writer). At 1000x (10PB table, continuous streaming, 100K writes/hour):

5.15 - First Principles Explanation

ACID in open table formats is an application of the IMMUTABILITY principle combined with the POINTER SWAP pattern.

Parquet data files are immutable. Once written, they never change. When a transaction updates rows: new Parquet files are written with the updated rows; old files are marked as “deleted” in the metadata. No in-place updates.

The ACID transaction is entirely in the METADATA, not in the data files. The transaction commits by atomically swapping the metadata pointer (version-hint.text) from the old version to the new version. This pointer swap is the single atomic operation. If it succeeds: the transaction is committed, readers see the new snapshot. If it fails: the data files exist on S3 (orphans) but no pointer points to them. They are invisible to readers and will be cleaned up later. ACID is free because immutable files + pointer swap is inherently atomic.

5.16 - Interview Tips

“How does Apache Iceberg achieve ACID transactions without a database server?”

Strong answer: “Iceberg uses three mechanisms:

Atomicity: all data files for a transaction are written to S3 before the commit. The commit is a single metadata file swap: atomically update version-hint.text from ‘v200’ to ‘v201’. Either the swap succeeds (all files visible) or fails (files exist as orphans, no reader sees them). One atomic operation = atomic transaction.

Isolation: snapshot isolation via immutable snapshots. Each reader reads a specific snapshot ID from the start of the transaction. Concurrent writes create new snapshots (v201, v202…) but don’t change the reader’s snapshot (v200). Readers never see partial writes.

Concurrency: optimistic concurrency control (OCC). No locks. Multiple writers try to commit concurrently. The commit CAS operation succeeds for exactly one writer; others get a conflict and retry. Works for write-light workloads; conflicts increase with many concurrent small writers (coalesce writes to reduce conflict rate).

The trade-off: no serializable isolation. Write skew is possible (two writers both read the same snapshot, make decisions based on it, both commit different rows without conflict). For constraints spanning multiple rows, implement application-level guards.”

5.17 - Surprising Truth

The most surprising operational fact about ACID open table formats is that GDPR right-to-erasure (the “right to be forgotten”) is NOT satisfied by a DELETE statement. An Iceberg or Delta Lake DELETE marks rows as deleted in metadata (equality deletes or tombstones) but the underlying Parquet files still contain the deleted rows physically. The data exists on S3. A determined person can read the old Parquet files directly (bypassing the table format metadata) and see the “deleted” data.

True GDPR deletion requires three sequential operations: (1) DELETE statement (marks rows as deleted in metadata), (2) REWRITE DATA FILES compaction (physically removes the deleted rows from Parquet files by rewriting them), (3) EXPIRE SNAPSHOTS + REMOVE ORPHAN FILES GC (deletes the old Parquet files that contained the deleted rows from S3). Only after all three steps are the deleted rows physically gone. Most data engineering teams stop at step 1 and claim GDPR compliance. They are wrong.

5.18 - Transferable Mental Models

Git for data mental model: The exact Git analogy: Parquet files = blobs, manifest files = trees, metadata files = commit objects, version-hint.text = branch pointer (HEAD). Snapshot chain = commit history. Time travel = git checkout. Orphan files = unreachable git objects (cleaned by git gc). Merge conflict = OCC conflict. Schema evolution = git rename with history preservation. The mental model is exact because Iceberg and Git solve the same fundamental problem: immutable content-addressed storage with atomic pointer swaps.

Database MVCC mental model: Iceberg’s snapshot isolation is equivalent to PostgreSQL’s MVCC (Multi- Version Concurrency Control). In PostgreSQL: rows are immutable (updates create new row versions, marked with commit timestamps). Readers see the version that was committed before their transaction started. Old versions are cleaned by VACUUM. Iceberg: files are immutable. Readers see the snapshot committed before their read started. Old files cleaned by expire_snapshots + remove_orphans. Same mechanism, different granularity (files vs rows).

5.19 - Memorable Framework

“AISD” - Open Table Format ACID properties:

  • Atomicity: pointer swap is the commit - one atomic operation; if it fails, nothing is visible
  • Immutability: data files never change after write; transactions create new files + mark old as deleted
  • Snapshot: readers always see a consistent snapshot; concurrent writes are invisible to in-flight reads
  • Detergent (cleanup): orphan files and expired snapshots must be periodically cleaned to control storage costs - ACID is only guaranteed if cleanup doesn’t delete files in the snapshot retention window

AISD is the checklist: all four properties must hold. Atomicity + Immutability are automatic. Snapshot is automatic. Detergent (cleanup) must be explicitly scheduled.

5.21 - Concept Fingerprint

Core invariant: In all open table format ACID implementations, the commit is atomic because the METADATA POINTER UPDATE is the single atomic operation. All data file writes happen before the commit; all metadata file writes happen before the commit; only the final pointer swap is atomic. This means: a partial write (process crash after data files but before commit) leaves orphan files on S3 but no committed state. Readers never see partial writes. The orphan files are cleaned by maintenance jobs.

Signature behavior: A correctly operating ACID open table environment has: scheduled expire_snapshots (weekly), scheduled remove_orphan_files (monthly), scheduled rewrite_data_files compaction (weekly for write-heavy tables), snapshot retention configured to match time travel needs (30 days is typical), and conflict monitoring (Iceberg’s numConflictedTransactions metric - high values indicate too many concurrent writers).

Boundary condition: Optimistic concurrency control fails under high writer concurrency. At 50+ concurrent writers, the retry storm (see failure mode 1) can cause write latency to spike from seconds to minutes. The solution: partition writers by write range (each writer owns a subset of partitions), use MERGE instead of separate writes (fewer, larger transactions), or switch to a serialized write queue (one writer at a time, other writers wait). ACID does not guarantee PERFORMANCE under high concurrency.

5.23 - Persona Pitch

For the data engineer: The first thing to set up after creating an Iceberg table is the maintenance schedule. Not a feature - maintenance. expire_snapshots weekly. remove_orphan_files monthly. rewrite_data_files weekly for tables with many small writes. Skip this and you will have a support ticket in 3 months: “why is S3 storage growing 10x faster than the data?” Answer: orphan files and unreferenced old snapshots. Schedule maintenance from day one.

For the analytics engineer: Iceberg time travel is your best debugging tool. When a stakeholder says “the revenue number changed since yesterday’s report,” you can say “let me compare yesterday’s snapshot vs today’s snapshot: SELECT * FROM orders TIMESTAMP AS OF '2024-01-14' vs SELECT * FROM orders TIMESTAMP AS OF '2024-01-15'.” Find the specific rows that changed. Identify which pipeline commit caused the change. Time travel turns “the data changed and we don’t know why” into a 5-minute investigation.

For the data platform architect: Evaluate the conflict rate for your Iceberg tables. If numConflictedTransactions is > 5% of total commits, you have a concurrent writer problem. Solution: redesign the write pattern (fewer, larger commits). One architectural pattern that eliminates conflicts: use a separate staging table per writer, then schedule one MERGE from all staging tables at the end of each load window. Zero conflicts (each writer has a unique staging table), one final commit per load window on the main table.
