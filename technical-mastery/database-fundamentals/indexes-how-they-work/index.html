⚡ TL;DR - An index is a separate data structure that maps column values to row locations, enabling the database to find rows without scanning the entire table. B-tree indexes are the default - they support equality (=), range (>, <, BETWEEN), and prefix (LIKE 'text%') queries in O(log n) time. Without an index, every query scans every row (O(n)). Indexes speed reads but slow writes (every INSERT/UPDATE/DELETE must update the index). The critical rule: index columns you filter on, join on, or sort by frequently; don’t index every column.

🔥 The Problem This Solves

THE PHONE BOOK PROBLEM:

A table has 10 million users. A query looks up a user by email: WHERE email = 'alice@example.com'.

Without an index, the database reads every row, comparing each email value to ‘alice@example.com’. For 10 million rows at 1 microsecond per comparison: 10 seconds per lookup. Unusable for a login API that must respond in under 100 milliseconds.

THE REAL SCALE:

A table that fits on one hard drive page takes microseconds to scan. A table that spans 100,000 pages takes 100 seconds. Query latency scales linearly with table size - not acceptable.

THE INVENTION MOMENT:

“Maintain a sorted auxiliary structure that maps column values to row locations. Finding a value in a sorted structure takes logarithmic time. A table of 10 million rows needs only ~23 comparisons to locate any value (log₂ 10,000,000 ≈ 23).”

This auxiliary structure is the index.

📘 Textbook Definition

An index is a database object that stores a sorted copy of the values from one or more columns, along with pointers (tuple IDs or row locations) to the corresponding table rows. Indexes allow the database engine to find rows matching a WHERE condition without reading the entire table.

B-tree index - the default index type in PostgreSQL, MySQL, and most relational databases. Stores values in a balanced tree structure supporting O(log n) equality and range lookups.

Index scan - query reads the index to find matching row pointers, then fetches those rows from the table. Efficient when a small fraction of rows match.

Sequential (full table) scan - reads every table row from beginning to end. Necessary when a large fraction of rows match (or no useful index exists).

Index types:

  • B-tree (default) - equality, range, ORDER BY
  • Hash - equality only; faster than B-tree for equality only
  • GIN (Generalized Inverted Index) - arrays, full-text search, JSONB containment
  • GiST - geometric data, range overlap, nearest-neighbor
  • BRIN (Block Range Index) - very large tables with natural ordering (e.g., timestamps); tiny index, less accurate
  • Partial index - indexes only rows matching a WHERE condition; smaller, faster for selective queries

⏱️ Understand It in 30 Seconds

One line: An index is a sorted lookup structure that lets the database find rows in O(log n) instead of O(n) by column value.

One analogy:

An index is a book’s index pages. Without an index, finding “database transaction” in a 1,000-page book means reading every page (sequential scan). With an index: look up “database transaction” in the index, find “page 247, 381, 512” - jump directly there.

The index itself is sorted alphabetically, so finding “database transaction” in the index takes O(log n) time (binary search). The tradeoff: the index occupies extra pages. Adding a chapter requires updating the index (write overhead).

One insight: Indexes don’t just change speed - they change time complexity. Without an index: O(n) - query time grows linearly with rows. With an index: O(log n) - query time grows logarithmically. For 1 million rows: O(n) = 1,000,000 operations; O(log n) = 20 operations. This is a 50,000x difference, not a 50% improvement.

🔩 First Principles Explanation

THE B-TREE STRUCTURE:

A B-tree index is a balanced tree where:

  • Each node contains multiple keys (column values)
  • Leaf nodes contain the key values + row pointers (TIDs)
  • Internal nodes contain key ranges + pointers to child nodes
  • All leaf nodes are at the same depth (balanced)
  • Leaf nodes are doubly linked (for range scans)

For a table with 1 million rows and a B-tree index:

  • Tree height: log₁₀₀ (1,000,000) ≈ 3 levels (branching factor ~100)
  • Lookup: 3 node reads → row fetch
  • Range scan: 3 reads to first node + sequential leaf page reads

WHY INDEXES SLOW WRITES:

Every INSERT requires inserting the new row’s indexed column values into every index on the table. Every UPDATE to an indexed column requires removing the old value from the index and inserting the new value. Every DELETE requires removing the row pointer from all indexes. A table with 5 indexes has 5x the write amplification compared to a table with no indexes.

SELECTIVITY - THE INDEX DECISION CRITERION:

Selectivity = fraction of rows matching the query condition.

  • WHERE email = 'alice@example.com' → 1/10,000,000 rows → HIGH selectivity → INDEX useful
  • WHERE status = 'active' (90% of rows are active) → LOW selectivity → INDEX often NOT useful
  • WHERE created_at > '2024-01-01' (last 3 months of 5-year table) → MEDIUM selectivity → INDEX useful

Rule: use an index when the query retrieves < 5-15% of rows. For > 15-20%, a sequential scan reading pages sequentially is faster than random page lookups via index.

📶 Gradual Depth - Five Levels

Level 1 - What indexes do (anyone can understand): An index makes finding rows faster. Without an index, the database checks every row. With an index, it jumps directly to matching rows. The cost: disk space and slightly slower writes (the index must be updated too). Add indexes on columns you frequently search or join on. CREATE INDEX idx_email ON users (email).

Level 2 - When indexes are used and when not (junior developer): Indexes work for: equality (=), range (>, <, BETWEEN), prefix LIKE (LIKE 'text%'), ORDER BY, JOIN conditions. Indexes don’t work for: functions wrapping the column (WHERE UPPER(email) = ...), leading wildcard LIKE (LIKE '%text'), very low selectivity queries (index on a boolean column rarely helps). EXPLAIN shows “Seq Scan” vs “Index Scan” vs “Bitmap Index Scan”. An index on a primary key is created automatically. UNIQUE constraint creates an index automatically.

Level 3 - Index types and when to use each (mid-level): B-tree (default): equality, range, ORDER BY. Hash: equality only - slightly faster for pure equality but no range support. GIN: for arrays, JSONB, full-text search (inverted index maps values to containing rows). GiST: for geometric data, PostGIS spatial queries, range overlap (e.g., booking date ranges). BRIN: for time-series tables ordered by date - stores min/max per block, tiny index, ideal for billion-row audit logs. Partial index: CREATE INDEX ON orders (customer_id) WHERE status = 'open' - only indexes open orders, dramatically smaller for tables where most rows are closed/delivered.

Level 4 - Index maintenance and bloat (senior): PostgreSQL uses MVCC (multi-version rows). DELETE and UPDATE don’t immediately remove old row versions from indexes - they leave “dead” index entries. VACUUM reclaims these. An index with many dead entries is “bloated” - performs worse and uses more disk. pg_stat_user_indexes shows index scans, unused indexes. pgstattuple shows bloat percentage. Index builds: CREATE INDEX CONCURRENTLY builds the index without locking the table (slower build, safe for production). Regular CREATE INDEX locks writes during build (fast but blocks). For heavily-written tables: always use CONCURRENTLY.

Level 5 - Index-only scans and covering indexes (staff): An index-only scan occurs when all columns needed by the query (SELECT and WHERE) are present in the index itself - the table data file is never accessed. CREATE INDEX ON orders (customer_id, status, created_at) with SELECT customer_id, status, created_at WHERE customer_id = 42 reads only the index, never the heap. This is dramatically faster for high-frequency queries on large tables. Limitation: index-only scan still requires checking the visibility map (which pages have been VACUUMed). If visibility map is not up to date: heap fetches are required anyway. VACUUM and autovacuum settings affect index-only scan effectiveness.

⚙️ How It Works (Mechanism)

B-TREE INDEX LOOKUP (EQUALITY):

Table: users (10M rows), B-tree index on email

Query: WHERE email = 'alice@example.com'

Index tree (height = 3):

Level 0 (root):
  [A-G] → node1  [H-N] → node2  [O-Z] → node3

Level 1 (node1):
  [A-Ca] → leaf1  [Cb-Ea] → leaf2  [Eb-G] → leaf3

Level 2 (leaf2 contains 'alice'):
  'alice@example.com' → TID (page 41287, slot 3)
  'alex@company.org'  → TID (page 9821, slot 7)
  ...

Execution:
  1. Read root: 'alice' in [A-G] → node1           (1 read)
  2. Read node1: 'alice' in [A-Ca] → leaf1         (1 read)
     actually [Cb-Ea] - sorry: alice < Cb → leaf1  (corrected)
  3. Read leaf1: find 'alice@example.com' → TID    (1 read)
  4. Fetch row from heap at TID                     (1 read)
  Total: 4 reads (vs 10 million for sequential scan)

RANGE SCAN - USING LINKED LEAVES:

Query: WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31'

1. B-tree search for '2024-01-01' → leaf node L1   (3 reads)
2. Scan L1 for all entries >= '2024-01-01'         (sequential)
3. Follow right-pointer to next leaf L2            (1 read)
4. Scan L2...
5. Continue until entry > '2024-01-31'
→ Reads only the relevant leaf pages, not all leaves
→ Then fetches all matching heap rows (random I/O)

flowchart TD
    Root["Root node\n[A-G] [H-N] [O-Z]"] -->|"alice in A-G"| I1["Internal node\n[A-Ca] [Cb-Ea] [Eb-G]"]
    I1 -->|"alice less than Cb"| L1["Leaf node\nalice@example.com - TID\nalex@company.org - TID"]
    L1 -->|"TID lookup"| Heap["Heap page\nactual row data"]
    L1 <-->|"doubly linked"| L2["Next leaf node"]

Diagram walkthrough: The B-tree index organizes values into a balanced hierarchy where root and internal nodes route the search, and leaf nodes hold the actual values and row pointers. For equality lookup: 3-4 node reads regardless of table size (logarithmic). For range scan: navigate to the start position, then scan leaf nodes sequentially (leaf nodes are linked), then fetch heap rows. The heap fetch (random I/O) is the expensive part for range scans with many results - this is why the planner switches to sequential scan above ~15% selectivity (sequential I/O is faster than random I/O for large fractions of the table).

💻 Code Example

BAD - Missing index on filtered column, too many indexes:

-- BAD: No index on email (users table, 10M rows)
-- Every login query does a 10M-row sequential scan
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    name VARCHAR(100),
    created_at TIMESTAMPTZ DEFAULT NOW()
);
-- No index on email → login query is O(n):
SELECT id FROM users WHERE email = 'alice@example.com';
-- PLAN: Seq Scan on users (cost=0..250000, rows=1)
-- Scans 10M rows to find 1 user

-- BAD: Indexing every column (over-indexing)
CREATE INDEX idx_users_name ON users (name);
CREATE INDEX idx_users_status ON users (status);
CREATE INDEX idx_users_phone ON users (phone);
CREATE INDEX idx_users_country ON users (country);
CREATE INDEX idx_users_created_at ON users (created_at);
-- Each INSERT now updates 5 extra indexes
-- Each UPDATE may update multiple indexes
-- Write amplification: 5-6x overhead on inserts
-- Many of these may never be used in production queries

Code walkthrough: The missing email index forces every login to scan 10 million rows - this is the login page being slow bug. The over-indexing example shows the opposite extreme: indexing every column creates massive write overhead. Every INSERT must update 5 B-tree structures. For a high-write table (events log, transactions), this can reduce write throughput by 5x.

GOOD - Strategic index creation:

-- GOOD: Index on frequently queried, high-selectivity column
CREATE UNIQUE INDEX idx_users_email ON users (email);
-- Login: O(log n) - ~20 operations for 10M rows
-- ALSO enforces uniqueness (like UNIQUE constraint)

-- GOOD: Composite index for common query pattern
-- Query: WHERE customer_id = $1 AND status = 'open'
--        ORDER BY created_at DESC
CREATE INDEX idx_orders_cust_status_date
    ON orders (customer_id, status, created_at DESC);
-- Covers all three: filter (customer_id, status) + sort (created_at)
-- Can answer: WHERE customer_id = $1 (leftmost prefix)
-- Can answer: WHERE customer_id = $1 AND status = 'open'
-- Can answer: WHERE customer_id = $1 AND status = 'open'
--             ORDER BY created_at DESC (index already sorted)

-- GOOD: Partial index for selective rows
-- 95% of orders are 'delivered' - ignore them in index
CREATE INDEX idx_orders_open
    ON orders (customer_id, created_at)
    WHERE status IN ('pending', 'processing');
-- Index size: 5% of full index (only open orders)
-- Query: WHERE customer_id = $1 AND status = 'pending'
--        AND status IN ('pending', 'processing')  ← must match partial
-- Much smaller and faster for open order lookups

-- GOOD: Functional index for case-insensitive lookup
CREATE INDEX idx_users_email_lower ON users (LOWER(email));
-- Now: WHERE LOWER(email) = LOWER($1) uses this index

-- GOOD: Create index without blocking table
CREATE INDEX CONCURRENTLY idx_products_category
    ON products (category_id);
-- Safe on production: doesn't lock the table
-- Slower build, but writes continue during index creation

Code walkthrough: Strategic indexing: email gets UNIQUE INDEX (enforces uniqueness AND speeds lookup - one structure for both). The composite index on (customer_id, status, created_at) covers the most common query pattern with a single index scan + no heap sort (ORDER BY is already in index order). The partial index is the key optimization for a table where most rows are in a terminal state - the index only covers active rows, staying small and fast as the table grows. CONCURRENTLY is always used for production tables to avoid locking out writes during the build.

FAILURE - Index not used due to implicit type cast:

-- FAILURE: Index exists but not used due to type mismatch
-- Column: user_id INTEGER, indexed
-- Application sends parameter as string (ORM serialization bug)

CREATE INDEX idx_orders_user ON orders (user_id);

-- Query sent by ORM (user_id cast to varchar accidentally):
SELECT * FROM orders WHERE user_id = '42';
-- In PostgreSQL: implicit cast from varchar '42' to integer
-- PostgreSQL CAN use the index here (it casts the constant, not column)
-- BUT some databases (MySQL, older versions) DON'T:
-- They cast the COLUMN to match the parameter type:
-- WHERE CAST(user_id AS VARCHAR) = '42'
-- → function on column → index not used → Seq Scan

-- Another common type mismatch:
-- Column: created_at TIMESTAMPTZ
-- Query: WHERE created_at = '2024-01-15'  (date literal, not timestamp)
-- PostgreSQL casts '2024-01-15' to TIMESTAMPTZ midnight UTC
-- Index IS used (constant side is cast)

-- CRITICAL type mismatch (index disabled):
-- Column: id BIGINT, NOT indexed separately (just PK)
-- JSON API sends: { "user_id": "42" } (string, not number)
-- ORM executes: WHERE id = '42'::text
-- If planner cannot cast the parameter safely: Seq Scan

-- Diagnostic:
EXPLAIN (ANALYZE)
SELECT * FROM orders WHERE user_id = '42';
-- If Seq Scan: check the actual type of user_id column
-- vs the parameter type being sent

-- Fix: ensure parameter types match column types exactly
-- Application: send numeric ID as integer, not string
-- PostgreSQL: use explicit cast in query: WHERE user_id = $1::INTEGER

Code walkthrough: Type mismatches between query parameters and column types can silently prevent index use. PostgreSQL is forgiving (it casts constants to column types), but some databases cast the column to the parameter type instead - wrapping the column in CAST() defeats the index. The most dangerous form: a JSON API that passes numeric IDs as strings, combined with an ORM that doesn’t explicitly type-cast parameters. EXPLAIN ANALYZE with the actual parameter type reveals whether the index is being used. The fix: ensure application code sends typed parameters matching the column’s declared type.

⚠️ Common Misconceptions

MisconceptionReality
“More indexes = faster database”Each index slows writes (INSERT, UPDATE, DELETE must update all indexes). Unused indexes waste disk space and write throughput. Only create indexes that are actually used by production queries.
“An index guarantees the query planner uses it”The planner uses statistics to estimate whether an index scan or sequential scan is cheaper. For low-selectivity queries (>15-20% of rows), the planner may choose a sequential scan even if an index exists. This is correct behavior.
“Indexes always make queries faster”For a 100-row table, a sequential scan is often faster than an index scan (index has overhead: read index node, then fetch heap row = 2 reads per result vs 1 sequential read). Indexes pay off on large tables with selective queries.
“UNIQUE constraint and UNIQUE INDEX are different objects”UNIQUE constraint creates a unique index automatically. They are the same underlying structure. CREATE UNIQUE INDEX and ALTER TABLE ADD CONSTRAINT ... UNIQUE produce identical results.

🚨 Failure Modes & Diagnosis

1. Missing Index Causing Sequential Scan on Large Table

Symptom: A specific query is slow. EXPLAIN shows Seq Scan on a large table. Adding LIMIT 1 doesn’t help (still scans all rows to find the first match). Query time increases with table size.

Root Cause: No index on the WHERE clause column(s).

Diagnostic:

-- Run EXPLAIN ANALYZE to confirm:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE email = 'alice@example.com';
-- Output: Seq Scan on users (rows=10000000)
-- Buffers: shared hit=50000 (reading 50000 pages)

-- Check existing indexes:
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename = 'users';

-- Check column cardinality:
SELECT COUNT(DISTINCT email) FROM users;
-- High cardinality → index will be very selective → create it

-- Fix:
CREATE INDEX CONCURRENTLY idx_users_email ON users (email);
-- Verify:
EXPLAIN (ANALYZE) SELECT * FROM users WHERE email = 'alice@...';
-- Now: Index Scan (rows=1, cost < 1ms)

2. Index Bloat Degrading Performance

Symptom: Index-related queries slow down over time on a table with high UPDATE/DELETE activity. VACUUM runs but performance doesn’t fully recover.

Root Cause: Index pages accumulate dead entries faster than VACUUM reclaims them (or VACUUM is not running frequently enough). Index pages are partly empty but not consolidated.

Diagnostic:

-- Check index bloat (requires pgstattuple extension):
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstattuple('idx_orders_status');
-- Look for: dead_tuple_percent > 10-20%
-- Also: free_percent (wasted space in pages)

-- Check index usage stats:
SELECT indexname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan DESC;

-- Fix (rebuilds index without bloat):
REINDEX INDEX CONCURRENTLY idx_orders_status;
-- Or: rebuild all indexes on a table:
REINDEX TABLE CONCURRENTLY orders;

3. Unused Indexes Degrading Write Performance

Symptom: INSERT/UPDATE operations are slower than expected. Table has many indexes. Removing one index significantly improves write throughput.

Root Cause: Indexes that are never (or rarely) used still have write overhead. Common: indexes created “just in case” that no production query ever uses.

Diagnostic:

-- Find indexes with zero or very few scans:
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,
    pg_size_pretty(pg_relation_size(indexname::regclass)) AS size
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
  AND idx_scan < 50  -- used fewer than 50 times since last stats reset
ORDER BY pg_relation_size(indexname::regclass) DESC;

-- Note: pg_stat_user_indexes resets on pg_stat_reset() or restart
-- Monitor for at least several weeks before dropping

-- Drop unused index:
DROP INDEX CONCURRENTLY idx_users_rarely_queried;

💎 Transferable Wisdom

Reusable Engineering Principle: “Every read-optimization creates a write-cost. The index is the fundamental example: sort once at write time, binary search at read time. The same trade-off appears everywhere in systems design:

Where else this pattern applies:

  • Search engines (Elasticsearch, Solr) - inverted index maps terms to documents. Building the index is expensive; querying is fast. Analogous to GIN index for full-text search.
  • Caching - a cache is an index to computed/fetched results. Write overhead: cache invalidation on mutation. Read benefit: O(1) cache hit vs O(n) computation.
  • Hash maps in application code - a HashMap is an in-memory hash index. Building it: O(n). Looking up: O(1). Memory cost. The same trade-off as a database Hash index.

The universal pattern:

read_cost = f(index_structure)    # log(n), O(1), etc.
write_cost += g(index_structure)  # update all indexes on write
space_cost += h(index_structure)  # index consumes space

Index design is always optimizing this three-way trade-off.”

💡 The Surprising Truth

A table with ZERO indexes can outperform a table with many indexes for write-heavy workloads. A time-series events table ingesting 1 million rows per second with 5 indexes on it can fail to keep up - each INSERT triggers 5 index updates (10 B-tree node writes). The same table with 0 indexes: 1 heap write per INSERT, 10x higher throughput. The common pattern for write-heavy time-series tables: drop all indexes during bulk load, then rebuild after. PostgreSQL’s COPY command bypasses index maintenance by default during initial loads. The insight: “index only what you query, not everything you might query.”

🎯 Interview Deep-Dive

Q1: What is an index and when should you add one?

Why they ask: Foundational performance knowledge for any backend role.*

Strong answer:

  • An index is a sorted auxiliary data structure mapping column values to row locations (tuple IDs). It enables O(log n) lookup instead of O(n) sequential scan.
  • B-tree (default): supports equality, range queries, ORDER BY. Most queries use B-tree.
  • Add an index when: (1) a column appears frequently in WHERE clauses, (2) it’s used in JOIN conditions, (3) it’s used in ORDER BY for large result sets, (4) it has high cardinality (many distinct values).
  • Don’t add when: (1) low cardinality (status with 3 values: index rarely helps for common values), (2) the column is rarely queried, (3) the table is small (sequential scan may be faster), (4) the table is write-heavy and every additional index slows writes.
  • Decision tool: EXPLAIN ANALYZE before and after. If removing a sequential scan saves more time than the added write overhead costs: add the index.

Q2: Why might the query planner ignore an existing index?

Why they ask: Tests deeper understanding of query planning.*

Strong answer:

  • Low selectivity: if the query matches >15-20% of rows, a sequential scan (reads pages sequentially) is faster than an index scan (random page reads per result row). The planner uses pg_statistics (column histograms) to estimate selectivity and may correctly skip the index.
  • Function on column: WHERE UPPER(email) = 'X' - the index stores raw email values, not UPPER(email). Planner cannot use the index.
  • Type mismatch: if the parameter type differs from the column type, some databases apply implicit casts to the column side, defeating the index.
  • Stale statistics: if ANALYZE hasn’t run recently, the planner’s row count estimates are wrong. It may underestimate rows and choose a sequential scan incorrectly (or vice versa).
  • NOT NULL / NULL behavior: certain null-related predicates may not use B-tree indexes efficiently.
  • Too small a table: the planner always prefers sequential scan for tables fitting in a few data pages - index overhead isn’t worth it.

Q3: What is a partial index and when would you use one?

Why they ask: Tests knowledge of advanced index optimization.*

Strong answer:

  • A partial index only indexes rows that satisfy a WHERE condition: CREATE INDEX ON orders (customer_id) WHERE status = 'pending'.
  • Benefits: (1) much smaller index size (only open/pending rows, not all rows), (2) faster index scans (smaller tree to traverse), (3) lower write overhead (only inserts/updates affecting pending rows update this index).
  • Use cases: (a) “Active” vs “closed” items - index only active. (b) NULL-specific queries: CREATE INDEX ON users (email) WHERE email IS NOT NULL - enforces uniqueness for non-NULL emails. (c) Status-based: audit tables where most rows are “completed” - index only “in-progress” for operational dashboards.
  • Limitation: the query must include the partial index’s WHERE condition to use it: WHERE customer_id = $1 AND status = 'pending' uses the index. WHERE customer_id = $1 (without status = ‘pending’) does not.

Q4: What is the difference between an index scan and a bitmap index scan in PostgreSQL?

Why they ask: Tests knowledge of physical execution strategies.*

Strong answer:

  • Index Scan: navigates the B-tree to find matching entries, then fetches each matching row directly from the heap (table). One heap fetch per matching row. Efficient for very few rows (< 100).
  • Bitmap Index Scan: navigates the B-tree and builds a bitmap of matching heap pages (not row TIDs). Then fetches ALL matching rows from each page in one sequential pass. More efficient when many rows match (reduces random I/O into sequential page reads).
  • When the planner chooses: for few rows (<100), Index Scan. For moderate rows (100-10,000), Bitmap Index Scan. For many rows (>10-15% of table), Sequential Scan.
  • Multi-index OR: WHERE a = 1 OR b = 2 with separate indexes on a and b. PostgreSQL can use Bitmap Index Scan on both indexes, then combine the bitmaps with OR logic, then fetch pages once. This allows two separate indexes to be combined for one query.

Q5: How does creating an index affect write performance?

Why they ask: Tests understanding of the read/write trade-off.*

Strong answer:

  • Every INSERT to a table with N indexes requires N+1 writes: 1 heap write + N index writes (one per index).
  • Every UPDATE to an indexed column requires deleting the old index entry and inserting the new one (2 index operations per updated index). PostgreSQL’s HOT (Heap Only Tuple) optimization avoids index updates when non-indexed columns are updated and the new version fits on the same page.
  • Every DELETE marks the heap row and all index entries as dead. VACUUM later reclaims them.
  • The write amplification factor: a table with 5 indexes has ~5-6x the write overhead of a table with no indexes.
  • Mitigation for bulk loads: (1) drop indexes before bulk INSERT, rebuild after. (2) Use COPY command (bypass-row-triggers mode). (3) Set maintenance_work_mem high for faster index builds.
  • Index build in production: always CREATE INDEX CONCURRENTLY to avoid locking writes during the build. Takes longer but allows the table to remain writable.

🔍 Concept Fingerprint

How to recognize index-related issues in code:

In SQL/EXPLAIN output:

  • “Seq Scan” on tables with millions of rows = potential missing index
  • “Index Scan” with low rows estimate = good
  • “Bitmap Index Scan” with many rows = moderate selectivity
  • “cost=0..250000” for a point lookup = no index

In query patterns that won’t use indexes:

  • WHERE UPPER(col) = ... or any function wrapping the column
  • WHERE col::text = '...' (type cast on column side)
  • WHERE col LIKE '%text%' (leading wildcard)
  • WHERE col != value (negation on low-cardinality column)

In schema:

  • Large table with no indexes other than primary key
  • High write rate + many indexes on same table
  • pg_stat_user_indexes showing zero idx_scan for some indexes

Diagnostic fingerprint: “Slow query on large table: EXPLAIN first. Seq Scan → check missing index. Index Scan but still slow → check selectivity, index bloat, or type mismatch. Many slow writes → check number of indexes.”

🚦 Failure Signature Index

Signature 1: Slow Point Lookup (Missing Index)

  • Pattern: single-row lookup slow; time grows with table size; EXPLAIN shows Seq Scan
  • Root cause: no index on WHERE column
  • Confirming test: EXPLAIN shows “Seq Scan” + “rows=1” (finds 1 row by scanning all rows)
  • Fix: CREATE INDEX CONCURRENTLY ON t (col)

Signature 2: Index Exists But Not Used

  • Pattern: EXPLAIN still shows Seq Scan despite index existing; query was fast before; performance degraded after column added
  • Root cause: function on column, type mismatch, or stale stats
  • Confirming test: EXPLAIN (ANALYZE) shows “Filter” instead of “Index Cond”; check parameter type vs column type
  • Fix: functional index, correct parameter type, run ANALYZE

Signature 3: Write Performance Degradation

  • Pattern: INSERT/UPDATE throughput declines; each batch insert slower than expected; pg_stat_user_indexes shows high write count vs low read count for several indexes
  • Root cause: over-indexing; indexes never used in reads but always updated on writes
  • Confirming test: idx_scan count near zero for some indexes over several weeks
  • Fix: drop unused indexes (after verifying with monitoring)
